# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | Startup / Global scope | No MongoDB indexes were created at startup. Unique constraints on `employees.emp_code` and `attendance_logs.(emp_code, date)` were not enforced at the database level, and listing/sorting queries would result in collection scans on ~100k records. | Inspecting database indexes at startup; concurrent requests could insert duplicates without DB-level unique constraint. | Created indexes idempotently during FastAPI lifespan: unique index on `employees.emp_code`, compound index on `employees.(department, emp_code)`, unique compound index on `attendance_logs.(emp_code, date)`, and compound index on `attendance_logs.(date, emp_code)`. Startup fails loudly and clearly if indexes cannot be created (errors are never silently swallowed). |
| 2 | `health` (`GET /health`) | Unconditionally returned `{"status": "ok"}` with HTTP 200 even when MongoDB was unreachable. OpenAPI contract requires 200 only if MongoDB answers a ping, else 503. | Calling `GET /health` with MongoDB server stopped returned 200 instead of 503. | Added `client.admin.command("ping")` within `try/except`, raising `HTTPException(503, "Database unavailable")` upon failure. |
| 3 | `create_employee` (`POST /employees`) | Used non-atomic check-then-insert (`find_one` followed by `insert_one`), causing race conditions under concurrent requests. Also unhandled duplicate error would yield 500. | Sending two concurrent POST requests with the same `emp_code` could insert duplicates or return 500. | Relied on MongoDB unique index on `emp_code`, caught `DuplicateKeyError` and raised `HTTPException(409, "emp_code already exists")`. |
| 4 | `EmployeeIn` model | Lacked schema validation required by OpenAPI `EmployeeCreate`: `emp_code` pattern `^EMP\d{4,6}$`, name/email/department lengths and formats, shift HH:MM regex, date format, and the rule that `shift_start` must differ from `shift_end`. | Sending invalid `emp_code="INVALID"` or `shift_start="09:30"` & `shift_end="09:30"` returned 201 instead of 422. | Added Pydantic `Field` patterns, constraints, and a model validator enforcing `shift_start != shift_end` and valid calendar date `joined_on`. |
| 5 | `create_employee` / `list_employees` | `created_at` used naive `datetime.now()` (local system time) and was returned as an ISO string instead of integer epoch milliseconds. Instants were not truncated to whole seconds (R1). | Response JSON showed string `created_at: "2026-07-06T09:30:00"` violating `EpochMillis` integer schema. | Truncated current UTC timestamp to whole seconds, stored as UTC BSON datetime in MongoDB, and converted to integer epoch milliseconds in API responses. |
| 6 | `list_employees` (`GET /employees`) | Off-by-one pagination bug: `skip = page * page_size`. Since `page` starts at 1, `page=1` skipped the first 20 records (`skip=20`), omitting the entire first page. | Calling `GET /employees?page=1&page_size=20` returned items 21–40 instead of items 1–20. | Fixed skip calculation to `skip = (page - 1) * page_size`. |
| 7 | `list_employees` (`GET /employees`) | `total = db.employees.count_documents({})` ignored the `department` query filter and always counted the entire collection. Rule R10 mandates `total` reflects applied filters. | Calling `GET /employees?department=Engineering` returned total count of all employees across all departments. | Updated count query to `total = db.employees.count_documents(q)`. |
| 8 | `list_employees` (`GET /employees`) | Missing sort order: documents were returned in natural database order. OpenAPI contract requires sorting by `emp_code` ascending. | Querying employees returned documents in arbitrary storage order. | Added `.sort("emp_code", 1)` to the cursor. |
| 9 | `compute_late_minutes` | Premature floor and grace period flaw: floored minutes before checking `> 10` (`minutes = int(total_seconds / 60); minutes if minutes > 10 else 0`). At 09:40:01 (601 seconds), floored minutes is 10, and `10 > 10` is False, returning 0 instead of 10 (Rule R2). | Test with punch-in at 09:40:01 for a 09:30 shift returned 0 instead of 10. | Evaluated `diff_seconds > 600` strictly, and if true, returned `diff_seconds // 60`. |
| 10 | `compute_late_minutes` | Naive datetime replacement: `punch_in.replace(hour=h, minute=m)` replaced UTC hour with IST hour directly, causing a 5.5 hour shift. Also did not handle timezone awareness properly. | Passing UTC punch-in (e.g. 04:35 UTC for 10:05 IST) compared 04:35 against 09:30 UTC, resulting in negative seconds. | Converted `punch_in` to IST (UTC+05:30) and truncated to whole seconds before comparing with IST shift start. |
| 11 | `compute_late_minutes` & `punch_in` | Did not implement Rule R1 for overnight shifts (`shift_end <= shift_start`). Punch-ins earlier than `shift_end` (e.g. 01:10 IST) belong to the shift that started the previous day. Starter code assigned next calendar day. | Punch-in at 01:10 IST for shift 22:00–06:00 resulted in date `2026-07-07` instead of `2026-07-06`. | Added `compute_attendance_date` implementing R1, and anchored `compute_late_minutes` to the shift start datetime of the attendance date. |
| 12 | `compute_work_hours` | Used Python built-in `round(..., 2)`, which implements banker's rounding (round half to even). Rule R4 strictly requires half-up rounding (e.g. 7.7075 hours -> 7.71, whereas banker's rounding gives 7.70). | Calculating work hours for 27747 seconds (7.7075 hrs) returned 7.70 instead of 7.71. | Used Python `Decimal` with `ROUND_HALF_UP` quantizing to `0.01`. |
| 13 | `compute_overtime` | Did not enforce the 30-minute minimum threshold (Rule R3). Any positive minutes were returned. | Punch-out 5 minutes after shift end returned 5 instead of 0. | Added threshold: `return minutes if minutes >= 30 else 0`. |
| 14 | `compute_overtime` | Failed to handle overnight shifts: `end` was anchored to `date_str` without advancing 1 day when `shift_end <= shift_start`, calculating > 1400 minutes false overtime. Also subtracting naive and aware datetimes raised `TypeError`. | Calculating overtime for shift 22:00–06:00 punched out at 06:40 IST next day returned > 1400 minutes. | Added overnight check advancing `end_dt` by 1 day when `shift_end <= shift_start`, and ensured both operands are aware in IST. |
| 15 | `punch_in` (`POST /attendance/punch-in`) | Raised unhandled `TypeError` (HTTP 500) when employee did not exist because `emp["shift_start"]` was accessed on `None`. Contract requires HTTP 404. | Calling punch-in with `emp_code="UNKNOWN"` crashed with 500. | Added check: `if not emp: raise HTTPException(404, "unknown employee")`. |
| 16 | `punch_in` (`POST /attendance/punch-in`) | Used non-atomic check-then-insert (`find_one` then `insert_one`), susceptible to race conditions under concurrent requests. | Concurrent identical punch-ins could bypass check and create duplicate records. | Relied on unique index `(emp_code, date)` on `attendance_logs` and caught `DuplicateKeyError` to return HTTP 409. |
| 17 | `PunchInIn` model | Accepted invalid status values (`ABSENT`, `LEAVE`) and invalid timestamps (floats, seconds). Contract restricts status to `[PRESENT, WFH, ON_DUTY]` and `punched_at` to strict integer epoch ms. | Punch-in with `status="ABSENT"` succeeded with 201 instead of 422. | Defined `PresenceStatusEnum` and validated `punched_at` using strict Pydantic `Field(strict=True, ge=100_000_000_000, le=4_102_444_800_000)`. |
| 18 | `punch_in` & `list_attendance` | Leaked internal database identifier by adding `"id": str(...)` to attendance records. Contract explicitly states attendance records have no id (addressed by natural key `emp_code, date`). | Response JSON contained unexpected `"id"` field violating `AttendanceRecord` schema. | Removed MongoDB `_id` and refrained from setting `"id"`. |
| 19 | `punch_in` & `list_attendance` | Returned `punch_in` and `punch_out` as Python datetimes (serialized as ISO strings) instead of integer epoch milliseconds. Also history timestamps were unformatted. | Response JSON contained `"punch_in": "2026-07-06T03:58:00"` instead of epoch milliseconds `1783310280000`. | Implemented `datetime_to_epoch_ms` formatter converting BSON/Python datetimes to integer epoch milliseconds. |
| 20 | `list_attendance` (`GET /attendance`) | Loaded entire collection into Python memory (`docs = list(db.attendance_logs.find(q))`) and performed sorting/pagination in RAM. Violates contract requiring fast execution on ~100k records without loading collection into memory. | Fetching attendance records caused unbounded memory allocation and slow response times at scale. | Delegated query execution, compound sorting, and pagination directly to MongoDB via `.count_documents(q)`, `.sort(...)`, `.skip(...)`, `.limit(...)`. |
| 21 | `list_attendance` (`GET /attendance`) | Missing secondary sort: only sorted by `date` descending, ignoring contract requirement to sort by `date` descending, then `emp_code` ascending. | Attendance records with the same date appeared in non-deterministic order. | Applied MongoDB sort `[("date", -1), ("emp_code", 1)]`. |
| 22 | `list_attendance` (`GET /attendance`) | Did not validate `date_from <= date_to`. Contract specifies: `date_from > date_to -> 422`. Starter returned 200 with empty list. | Querying `GET /attendance?date_from=2026-07-10&date_to=2026-07-01` returned 200 instead of 422. | Added validation raising `HTTPException(422, "date_from must be <= date_to")`. |
| 23 | Helper functions | Missing helper for Rule R5: half-day calculation (`half_day = true when rounded work_hours < 4.50`). | Code lacked helper to compute half-day flag according to R5. | Added `compute_half_day(work_hours: Optional[float]) -> bool`. |

Also note anything you looked at and decided was **not** a defect, and why:

1. **Endpoint paths and HTTP methods:** All existing endpoint paths (`/health`, `/employees`, `/attendance/punch-in`, `/attendance`) and their HTTP methods match `openapi.yaml`.
2. **Default pagination parameters:** Default `page=1` and `page_size=20` correctly align with Rule R10 and OpenAPI schema defaults.
3. **HTTP 201 on employee creation & punch-in:** Both endpoints correctly return HTTP 201 Created on successful execution as specified in the API contract.
4. **Default employee shift times:** Default `shift_start="09:30"` and `shift_end="18:30"` in `EmployeeIn` match the defaults specified in `openapi.yaml`.
5. **Default punch-in status:** Default `status="PRESENT"` in `PunchInIn` matches the OpenAPI contract.
6. **IST timezone definition:** The definition `IST = timezone(timedelta(hours=5, minutes=30))` correctly represents Indian Standard Time (UTC+05:30).
7. **Rejection of equal shift times (`shift_start == shift_end`):** While Rule R1 states that overnight shifts satisfy `shift_end <= shift_start`, `openapi.yaml` explicitly specifies under `POST /employees` that `shift_start must differ from shift_end`. Therefore, overnight shifts are properly supported when `shift_end < shift_start` (e.g. 22:00 to 06:00), while identical shift times (`shift_start == shift_end`, which would represent an impossible 0-hour shift) are strictly prohibited and correctly return 422.
